# Trend-Tree

McClatchy's data pipeline that ingests cultural signals, identifies trends, and surfaces them on the **ATLAS** dashboard in the Insights Agent for marketing strategists and content teams.

## Language

**ATLAS**:
The main trend dashboard UI in the Insights Agent — the trend list / trend cards view. The audience for `docs/dashboard/`.
_Avoid_: "trend dashboard" (ambiguous with `DT_TREND_DASHBOARD`), "Insights Agent dashboard" (the Insights Agent has multiple UI surfaces — Predictions Queue, Collections, Decision Page — not all of them are ATLAS).

**DT_TREND_DASHBOARD**:
The Snowflake dynamic table (`MCC_PRESENTATION.TREND_AGENT.DT_TREND_DASHBOARD`) that ATLAS queries. One row per trend; 15-minute refresh lag.
_Avoid_: "the dashboard view" (V_TREND_DASHBOARD was dropped 2026-04-28; this is now a dynamic table).

**Signal**:
One individual data point ingested into the pipeline. Has exactly one source and (usually) one publisher. Stored in `FCT_SIGNALS`.

**Source**:
The integration / workflow that brought a signal into the pipeline. The name in `FCT_SIGNALS.SOURCE_NAME` — e.g., `bluesky`, `gdelt`, `google_trends_explore`, `amazon_trends`, `gemini_food_drink`, `agent_gemini_discovery`. ~14 distinct values today. The name identifies the **platform/origin, not how the signal entered** (see [Flagged ambiguities]). Three entry mechanisms:
- **Direct platform source** — a scheduled ingester pulls passively from one platform's API or feed (`amazon_trends`, `wikimedia`, `tiktok`, `pinterest`, `google_trends_rss`, plus the passive half of `bluesky` / `google_trends_explore`).
- **Discovery agent** — an LLM that, on a cron, **proactively proposes** emerging trend topics not already in the active list; we post-verify the returned URLs before ingest. Output is **authored proposals** (Grok/Gemini/ChatGPT coin a topic + title), not raw platform data (`agent_gemini_discovery`, `agent_grok_discovery`, `agent_chatgpt_discovery`, and the vertical-sharded `gemini_food_drink`/`other`/`travel`/`wellness`).
- **Agent search tool** — an ingest tool a reasoning agent (distillation, enrichment) calls **on-demand with a specific query**, persisting the results as signals for grounding. Reactive, not scheduled. The four tools are `search-bluesky`, `search-gdelt`, `search-google-trends`, `grok-live-search` (writing source names `bluesky`, `gdelt`, `google_trends_explore`, `grok_live` respectively). Each owns a distinct lane: `grok-live-search` is **X-only** (`x_search`, social), `search-gdelt` is news, `search-google-trends` is search demand, `search-bluesky` is social.

_Avoid_: "platform" (too vague — could mean source or publisher), "ingestion source" (just say "source"); never call an [agent search tool] a [discovery agent] — discovery is proactive and cron-driven and authors topics; a search tool is reactive, agent-driven, and answers a supplied query.

**Publisher**:
The actual website or property a signal originates from — e.g., `nytimes.com`, `vox.com`, `bsky.app`, `wikipedia.org`. Extracted from the signal's metadata. **What `DISTINCT_PUBLISHER_COUNT` actually counts** — four GDELT articles from four publishers count as 4, not 1.
_Avoid_: "domain" in user-facing copy (technically synonymous but feels technical); "outlet" (used for paid-media in other McClatchy contexts).

**Authored citation**:
A source URL the model **chose to cite in prose it wrote** — selected by the model's own reasoning, not by the search runtime. Both Grok avenues emit these: a [discovery agent] authors a `{topic, evidence_url, why_now}` proposal and hand-picks one `evidence_url` (web + X); the `grok_live` [agent search tool] authors a `{summary, citations:[{url, context}]}` object of real X posts (X-only, since 2026-05-28). Because the model curated it, titles are clean and X links keep the real `x.com/<handle>/status/<id>` form. Read from the model's message text via balanced-delimiter matching (`discover_grok` → `extractJsonArray`; `fetch_search` → `extractJsonObject`).
_Avoid_: conflating with [native citation] — both are URLs in the same xAI response, but only the authored one passed through the model's judgment.

**Native citation**:
A source URL xAI's tool-runner **auto-tracked** while answering a query — bookkeeping, not curation, read from the response's `data.citations` array. Because no model judgment selected it, the `title` is only a reference index (`"1"`, `"2"`…, see memory `xai_grok_api_migration`), X links come back anonymised as `x.com/i/status/<id>`, and there is no per-citation context. **Consumed by nothing as of 2026-05-28** — `grok_live` used to persist these (one shared summary reused as every row's `SIGNAL_TEXT`) but was switched to [authored citation]s when it became X-only. Kept as a named anti-pattern.
_Avoid_: assuming a native citation's `title` is a page title (it is not); reviving `data.citations` as a signal source.

**Link kind**:
The provenance of a `FCT_TREND_SIGNALS` row attaching a signal to a trend — either `'supporting'` (the signal underwrote the candidate that became this trend; written by `TASK_PROMOTE_TREND_SIGNALS` from `STG_TREND_CANDIDATES.SUPPORTING_SIGNAL_IDS` once per promotion/dedup) or `'attributed'` (written later by `lifecycle-attribution-subagent-p_PACe77B` when a newly-arrived signal is semantically matched into an existing trend at lifecycle-sweep time). **Mutually exclusive per `(trend_id, signal_id)` pair** — `'supporting'` always wins, because the attribution agent's NOT EXISTS guard ignores `LINK_KIND` and skips any pair already linked. The two kinds have very different freshness profiles: supporting is spiky and gated on promotions firing; attributed is steadier and gated on the lifecycle sweep cron.
_Avoid_: `'evidence'` — documented as a planned third kind in `sql/fct_trend_signals.sql:9-33` but never implemented. The enrichment agent's typed citation pool lives in `FCT_TREND_ENRICHMENT_LEDGER.PAYLOAD:evidence`, not in the link table; the lifecycle-attribution agent replaced the original "enrichment-writes-evidence" plan.

**Trend topic**:
The trend's raw identity string — coined at promotion time by Cortex. Lives in `FCT_TRENDS.TREND_TOPIC`. **Identity** — frozen at promotion, never re-derived, audience is the pipeline (grouping/deduplication), not strategists. Strategists see [trend name] on ATLAS, not [trend topic]. Topic survives as the last-resort fallback when no enrichment has produced a name yet.
_Avoid_: conflating with [trend name] — they share a table but serve different audiences and freeze at different lifecycle points.

**Trend name**:
The clarity-first, human-facing name on every ATLAS card (e.g., "Tallow Renaissance", "Liquid Room Architecture for Hybrid Living"). Lives in `FCT_TRENDS.TREND_NAME`. **Frozen at first enrichment** via `PROC_ENRICHMENT_APPLY` (guarded `WHERE TREND_NAME IS NULL`); re-enrichments emit new candidates to `FCT_TREND_ENRICHMENT_LEDGER.PAYLOAD:name_candidates_considered` but cannot overwrite the canonical name. **Foot-gun — "first enrichment" means first run that emits a *singular* name, which for legacy trends is a later re-run:** a trend first enriched under the legacy dual-name agent has `TREND_NAME_B2C`/`B2B` set but singular `TREND_NAME` still NULL, so the proc's block-2a guard (`WHERE TREND_NAME IS NULL`) stays open. The *next* re-enrichment under the singular-name agent is a **backfill** that freezes `TREND_NAME` from its payload — silently renaming the trend's ATLAS card (observed 2026-05-28: re-running enrichment on the legacy "Plot-Driven PTO" trend froze `TREND_NAME = "The Reader's Retreat"`, since the COALESCE chain prefers `t.TREND_NAME` over `t.TREND_NAME_B2C`). To restore the legacy name, explicitly pin `FCT_TRENDS.TREND_NAME` (setting it back to NULL only re-opens the guard for the next re-run). Replaces the dual B2B/B2C emission (singular-name cutover designed 2026-05-27; ships when the schema migration + active-trend re-enrichment land). Convention: clear coined phrase, 2–8 words preferred, no hard cap. **Binding rule is `decode_pass`** — a strategist seeing only the name (no topic, no card context) must be able to identify the trend's core subject; enforced at the reviewer step via a two-call test (decoder reads name alone and writes a one-sentence guess; verifier compares the guess to the topic and returns `decode_pass: bool`). One beat suffices when the first noun names the trend's core substance (e.g., "Tallow Renaissance" — tallow IS the trend); a second qualifier beat is required when the first beat is metaphoric or non-self-locating (e.g., "Liquid Room Architecture for Hybrid Living"). Two-beat is an *outcome* the agent reaches when the metaphor can't self-locate, not a structural mandate. **Tier-1 hard rule (mechanical):** the first-beat noun may not be a category-of-change word (`architecture, maximalism, minimalism, wellness, modernism, movement, era, wave, mode, aesthetic, vibe, paradigm, philosophy`) — these describe the shape of a shift, not the substance of it, and belong in the qualifier beat if anywhere. The corporate-media floor still applies — sales-deck-safe, no crude or insult-coded names. Register sits between today's `TREND_NAME_B2B` (descriptive) and `TREND_NAME_B2C` (creative-poetic), favoring "the metaphor teaches" over "the metaphor decorates."
_Avoid_: "display name" (the column is `TREND_NAME`; "display" reads as UI-layer, but freezing is identity-layer); "B2C name" / "B2B name" (the dual emission is retired — only legacy enriched trends still carry those values, see [legacy audience names]); "two-beat name" (the rule is decode, not structure — a second beat is an outcome of failing decode_pass, not a mandate).

**Trend descriptor**:
The machine-facing canonical representation of what a trend *is* — authored by the enrichment agent after grounding, the de-buzzworded counterpart to the evocative [trend name]. A nested object at `FCT_TREND_ENRICHMENT_LEDGER.PAYLOAD:descriptor` with two authored members: `statement` (the faithful prose core — the seed the embedding doc is built from, and the substrate for semantic matching / future collections) and `query` (a short **atomic, consumer-vernacular** catalog/search term — the single ingredient/product/practice a shopper would search, *not* a compound behavior, coined label, or industry jargon — for external keyword APIs; first consumer Exploding Topics; generalizes [gtrends search keyword]). **Audience is other systems, not strategists** — the opposite register from [trend name] (human, evocative), and higher-fidelity than [trend topic] (the cheap promotion-time identity seed). Thin per-consumer adapters reshape `query`/`statement` for each API (ET keyword, GDELT boolean) rather than schema-ing every consumer's shape onto the object. **Evolving on the ledger** (latest-non-null per trend), like `TREND_VECTOR` — never frozen, because the embedding it seeds is a drift-tracking time series and a sharper machine representation is a pure improvement (no human-visible rename to protect, unlike [trend name]). `statement` is a tight 2–4-sentence faithful paragraph and is the **sole** input to the embedding doc (`FN_TREND_EMBED_DOC`), replacing the legacy `topic | summary_long | drivers | narrative` concatenation — focus beats volume for identity similarity (drivers/narrative dilute the identity vector). Cutover gated on a measured neighbor-quality check.
_Avoid_: conflating with [trend topic] — topic is the promotion-time, frozen, ≤80-char dedup/lineage seed coined by Cortex; the descriptor is the enrichment-time, research-informed successor that takes over the embedding-seed role. Not a "summary" ([trend name]'s `summary_short`/`summary_long` are action-oriented *human* output); not human-facing.

**Legacy audience names**:
The retired dual emission — `FCT_TRENDS.TREND_NAME_B2C` ("Plush Architecture"-style creative) and `FCT_TRENDS.TREND_NAME_B2B` ("Tactile Maximalism"-style descriptive). Frozen on trends enriched **before** the singular-name cutover (2026-05-27 design; date stamped when the cutover actually ships). Kept on the table for back-compat — `DT_TREND_DASHBOARD.TREND_NAME` falls back through B2C → B2B → topic for any trend that hasn't been re-enriched under the new prompt. No new code should emit or consume these; they're a fallback, not a target.

**Gtrends search keyword**:
The 2–4 word query the gtrends-poller submits to Google Trends to compute a trend's `INTEREST_PEAK_PCT`. Lives in `FCT_TRENDS.GTRENDS_KEYWORD`. **Mutable lookup helper** — not identity. Set at promotion via Cortex `mistral-large2` for cost reasons, but may be re-derived later if it's returning empty timeseries. Audience is the Google Trends API, not humans.
_Avoid_: conflating with [trend topic] — they share an origin column at promotion time but are conceptually distinct. The trend topic is descriptive prose for marketers; the search keyword is a consumer-vernacular query string for a machine. Also distinct from [gtrends trending query].

**Gtrends trending query**:
The 1–3 word search query (e.g., `kali uchis`, `nba finals`) that anchored a batch of related news articles in the Google Trends RSS feed at ingest time. After the 2026-05-27 flatten, lives in `FCT_SIGNALS.METADATA.gt_trending_query` on every `google_trends_rss` row. **Provenance tag, not identity** — flattened articles are first-class signals; the trending query is recoverable metadata, not a row in any table. Relationship to [trend topic] is **many-to-many**: one trending query's articles can attach to several trends if headlines diverge, and one trend can be underwritten by articles from multiple trending queries.
_Avoid_: conflating with [gtrends search keyword] — both are short query strings but they live in different tables for different audiences. The search keyword is on `FCT_TRENDS`, written at promotion, polled against the GT Explore API. The trending query is on `FCT_SIGNALS.METADATA`, copied from the RSS feed at ingest, never re-derived.

## Flagged ambiguities

**`SOURCE_NAME` does not encode the entry mechanism.** A signal's source name tells you the platform/origin, not how it arrived — the [Source] mechanism (passive ingester vs. [agent search tool]) is an orthogonal axis. Three names are mixed- or tool-provenance: `bluesky` and `google_trends_explore` are written by *both* a passive ingester *and* an [agent search tool]; `gdelt` is now written *only* by the search-gdelt tool (the passive GDELT batch ingester was retired 2026-04-26); `grok_live` is the lone agent-search-tool output with a dedicated name (no passive "grok" platform exists). To tell whether a given signal came from passive ingestion or an agent tool call, inspect `METADATA` (tool calls carry `search_query`) — not `SOURCE_NAME`. **This shared naming is accidental, not designed** (confirmed 2026-05-28): the [agent search tool]s simply reused the platform label. It's a known cleanup target — tool-sourced signals should carry separable provenance (a dedicated source name, or a `METADATA` provenance flag) so passive vs. tool signals don't require parsing `search_query`. Until that lands, treat `bluesky` / `gdelt` / `google_trends_explore` as mixed-provenance.

**The two Grok searches are different mechanisms.** `agent_grok_discovery` is a [discovery agent] (the `discover_grok` step in `discovery-p_5VCPP3N`, cron every 2h): Grok proactively proposes trend topics across web + X and authors its own descriptive title. `grok_live` is an [agent search tool] (`grok-live-search-p_vQCkkGK`, registered in the shared `agents/lib/tool_catalog.mjs`): distillation/enrichment agents call it with a specific query and it returns a digest summary + 3–8 cited X posts. Same xAI API (grok-4, `/v1/responses`); they still differ on two axes:
- **Intent direction** — discovery is Grok *telling us what's new* (proactive, cron-driven, web + X); live-search is an agent *asking Grok about something specific* (reactive, query-driven, **X-only** — web/news/demand grounding is owned by GDELT + Google Trends).
- **Post-processing discipline** — discovery reranks + HEAD/GET-verifies + freshness-filters + dedupes web articles before write; `grok_live` runs a cheap no-network X-URL gate (canonicalize to `x.com`, drop non-X, extract `<handle>`, flag anonymised `/i/`, dedupe) — x.com can't be scraped, so trust rests on Grok's authoring discipline, not verification.

Both now consume [authored citation]s, so the old title-quality / anonymised-`x.com/i/status` URL-form gap is closed at the source (it was the root cause; see [native citation] for the abandoned `data.citations` path).

**`grok_live` is the X/social-only avenue (2026-05-28 refactor).** `grok_live` signals are first-class — they enter distillation's claimable pool (~190/day, `acquire_signal_ids/entry.js:16-20`), get clustered (`PROC_CLUSTER_SIGNAL_SUBSET`), can be attributed into trends by lifecycle-attribution, and are mapped to the `x.com` publisher in `lifecycle-subagent` + `prediction-agent`. Previously the tool searched web + X and MERGE'd ungated [native citation]s at ~6x discovery's volume, so most rows were low-quality web citations redundant with GDELT — and the hardcoded `grok_live → x.com` publisher mapping was *wrong* for them. The fix scopes the tool to **X-only** ([authored citation]s of real posts + the cheap X-URL gate): cuts the volume, fixes X title/URL quality at the source, makes the `→ x.com` mapping correct, and gives each grounding avenue a distinct lane (Bluesky + grok_live = social; GDELT = news; Google Trends = demand — see memory `grok_live_is_x_social_only`). Residual trust note: X posts still can't be web-verified (x.com blocks scraping), so a `grok_live` URL's existence rests on Grok's authoring discipline; `METADATA.anonymised=true` flags any post Grok couldn't resolve to a `<handle>`.

**`DISTINCT_SOURCE_COUNT` is misnamed.** The column counts distinct **publishers**, not sources. Canonical replacement `DISTINCT_PUBLISHER_COUNT` was added to `DT_TREND_DASHBOARD` on 2026-05-26 as a sibling alias (same value, new name), following the `VELOCITY_DIRECTION` / `LIFECYCLE_STATUS` pattern. The legacy `DISTINCT_SOURCE_COUNT` is kept for back-compat. Prefer `DISTINCT_PUBLISHER_COUNT` in any new query or display; the Insights Agent UI migrates from the legacy name when convenient.

**"Trend" vs "candidate".** A *candidate* is a `STG_TREND_CANDIDATES` row proposed by the distillation agent. A *trend* is a candidate after the promotion agent has accepted it (one `FCT_TRENDS` row + a `FCT_PROMOTION_LEDGER` entry). ATLAS only ever shows trends. Resolved here for the doc; if any term collisions arise during writing, refine.

**`FCT_TRENDS` is mostly-but-not-entirely identity.** CLAUDE.md describes it as "slim, immutable, identity (13 cols)" after the 2026-04-28 agent-owned-ledgers refactor. That's true of most columns (`TREND_ID`, `CANDIDATE_ID`, `TREND_TOPIC`, `DETECTED_AT`, `PROMOTED_AT`), but `GTRENDS_KEYWORD` is a **mutable lookup helper** that sits on the same table for convenience (cheap to set once at promotion, no separate writer to maintain). Re-deriving it does not violate trend identity. If more mutable helpers accrue on `FCT_TRENDS` they should be called out the same way, or the column should move to a dedicated mutable table.

**Empty `INTEREST_OVER_TIME` array ≠ low search volume.** Google Trends Explore returns empty `timelineData` for *both* "this keyword genuinely has insufficient search data" *and* "you look like a bot, here is a silent rate-limit response." The poller's `INTER_TREND_SLEEP_MS = 3_000` comment in `gtrends-poller-p_13CN9KG/fetch_and_compute/entry.js:16` is the only place that fact is encoded today. Diagnosing GT poller failures requires probing the same keyword in the GT UI (browser, residential IP) before concluding the keyword is the problem — confirmed 2026-05-27 when `Korean spicy ramen` returned strong data in the UI but 8/9 empty days from the poller.

**`INTEREST_PEAK_PCT` is always 100 when non-empty.** Google Trends normalizes single-keyword timeseries so the highest point of the returned curve equals 100 by definition — that's the GT normalization convention, not a measurement. `FCT_TREND_GTRENDS_DAILY.INTEREST_PEAK_PCT` is therefore a *binary* indicator (`100` = "any data," `0` = "empty/blocked"), not a continuous one. **`INTEREST_AVG_PCT` is the continuous measure** — captures sustained interest vs single spike. The lifecycle subagent's `external_factor` switched from peak to avg on 2026-05-27 (`lifecycle-subagent-p_gYC562o/run_subagent/entry.js:255-265`); any new consumer of GT data should likewise prefer avg unless they explicitly want the binary "did the poll succeed" signal.
