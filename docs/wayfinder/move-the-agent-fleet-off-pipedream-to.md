# Map: move the agent fleet off Pipedream to GCP

> Migrated from [mjmena/Trend-Tree#82](https://github.com/mjmena/Trend-Tree/issues/82) on 2026-08-07; comment history remains on GitHub. `#N` references in this body refer to the GitHub archive; blocking edges among then-open issues were recreated as JIRA links (repaired 2026-08-07 — the original migration had dropped them).

## Destination

A locked, handoff-ready **migration spec** for moving the **entire Trend Tree agent fleet** off Pipedream and onto Cloud Run in the shared `mcc-crm-automations` GCP project (`us-east4`). Delivered as **one reusable extraction template plus a phased migration sequence**, with the enrichment agent (`enrichment-p_xMC995w`) as the worked, prototype-backed example — not a spec per agent.

**The end state is a full Pipedream exit.** Hybrid — agents on Cloud Run, glue and cron still on Pipedream — is an explicit **transition phase**, not the destination.

| Phase | Scope | Gate |
|---|---|---|
| **1** | enrichment → Cloud Run, Pipedream dispatcher still calling it | specified end-to-end (CRMA-435–443) |
| **2** | the remaining agents, same template | → [CRMA-537](https://mcclatchy.atlassian.net/browse/CRMA-537) |
| **3** | scheduler + glue tier + monitoring redesign → Pipedream deleted | → [CRMA-534](https://mcclatchy.atlassian.net/browse/CRMA-534), [CRMA-535](https://mcclatchy.atlassian.net/browse/CRMA-535) |

Production stays live throughout this map; execution happens after handoff via `/to-prd` → `/to-issues`.

> **Amended 2026-08-09 (destination redrawn — Martin's call).** This map previously targeted **one agent** (enrichment) plus a reusable pattern, with the cluster-agent and the glue tier both explicitly out of scope. Both are now **in scope**, and the end state moved from "enrichment on GCP" to "no Pipedream". The seven decisions already locked (CRMA-435–443) all survive — they were written pattern-reusable — with one reframe: [CRMA-443](https://mcclatchy.atlassian.net/browse/CRMA-443) is now the **transition-phase** monitoring decision, correct until the dispatcher itself leaves, at which point CRMA-535 takes over.
> 
> **Earlier amendment (2026-08-09):** the destination once read "a **new dedicated** GCP project". [CRMA-437](https://mcclatchy.atlassian.net/browse/CRMA-437) reversed that — the host is the existing shared project.

## Notes

- **Motivation** (weight it in every comparison): Pipedream's testing and iteration loop feels restrictive — no local execution, no debugger, commit-to-deploy for every tweak, ~5.5-min HTTP sync cap. Dev-loop ergonomics outrank raw runtime fit.
- **Settled during charting / rechartering** (no tickets behind these): destination is a spec, not an executed migration; the spec is **prototype-backed**; the deliverable is **one template + a sequence**, never a spec per agent; enrichment is the worked example and moves first; hybrid is a transition, full exit is the end state. ~~Host is a new dedicated GCP project~~ — superseded by CRMA-437. ~~Scope is enrichment plus a reusable pattern~~ — **superseded 2026-08-09: the scope is the whole fleet.**
- **The fleet, counted 2026-08-09**: 18 workflows call an LLM API directly. Grouped logically — discovery + 4 Gemini verticals, distillation lead + subagent, the shared cluster-agent, revisit + subagent, promotion agent, enrichment, lifecycle + subagent, lifecycle-attribution + subagent, audit — plus the `grok-live-search` tool. Two boundary cases: `sources` is treated as glue but calls Anthropic at `sources-p_7NCy36w/generate_search_terms/entry.js:95`; `prediction-agent` is **not** an LLM agent despite the name (deterministic SQL).
- **Widening deletes work as well as adding it.** `distillation` and `distillation-revisit` both reach the shared cluster-agent through `$.flow.suspend`, a pattern that exists purely to dodge Pipedream's ~5.5-min HTTP cap. Cloud Run request timeouts reach 60 min, so at fleet scale that entire suspend/resume mechanism collapses into an ordinary synchronous call. **The same shape recurs one level down** — the four ingest tools are separate workflows only because a workflow is Pipedream's sole unit of reuse; on Cloud Run they collapse into library modules (→ CRMA-493).
- **Facts**: `gcloud` authed as `mmena@mcclatchy.com`. `gh` installed and authed as `mjmena`. Enrichment runs 3–5 min wall-clock, ~$0.40–0.50/run p95, one caller (`dispatcher-p_8rCBgnl`), sync contract `POST {trend_id}` → JSON. **Enrichment is read-*****mostly*****, not read-only, on Snowflake** — `tag_signals` (`enrichment-p_xMC995w/workflow.yaml:321`) runs an `UPDATE` on `STG_EXTERNAL_SIGNALS`, and CRMA-493 adds the tools' `MERGE_EXTERNAL_SIGNALS` call, so **the extracted service needs write**. (`CLAUDE.md` still says read-only — correct it at spec time.) Snowflake role is `MARKETING_ENGINEER` (not ACCOUNTADMIN); no Snowflake network policy exists, so Cloud Run egress is unblocked. **GCP observability (probed 2026-08-09): every read granted** (`logging.logEntries.list`, `logging.logMetrics.get`, `monitoring.timeSeries.list`, `monitoring.alertPolicies.list`, `monitoring.notificationChannels.list`, `errorreporting.groups.list`), ~~every create denied — GCP can never *push* an alert~~ — **superseded 2026-09-28 (CRMA-497): `alertPolicies.create`, `notificationChannels.create`, `logMetrics.create` and `uptimeCheckConfigs.create` are now granted**, so GCP can push an alert by email (precedent: the Harbor liveness policy). `pubsub.topics.create` and every billing-budget write stay denied. ~~Every scheduler/event primitive is denied too~~ — **superseded (probed 2026-09-28, CRMA-534): Cloud Scheduler is granted** (since 2026-08-20; four Trend Tree jobs already run on it) **and so is `serviceusage.services.enable`**. ## Standing constraints

- **Cloud Run scaling posture is chosen by service shape** ([CRMA-496](https://mcclatchy.atlassian.net/browse/CRMA-496)). Each service sets every value explicitly in its `deploy.env`; the `services/deploy.sh` fallbacks stay unchanged.
  - **Agent loop** (long, LLM-bound, low volume — enrichment, cluster-agent, lifecycle subagents): `--concurrency 1`, `--min-instances 0`, `--max-instances` = 2× the observed peak burst.
  - **Short request** (seconds — e.g. ecomm-agent): the `deploy.sh` defaults, concurrency 10, max 5, min 0.
  - **Timeout, every shape:** the service timeout nests inside its caller's timeout (inner < outer); never the 300 s default.
  - **Enrichment's values:** concurrency 1, min 0, max 8, timeout 480 s (the dispatcher's enrichment hop gives up at 500 s inside a 600 s `lambda_timeout`).
  - **Revisit** when the caller changes (CRMA-528's invocation model, the phase-3 exit): recompute the timeout from the new caller; if the caller becomes a poll, recompute max-instances from the poll batch size.
  - `--max-instances` bounds the *rate* of LLM spend, not the total; the runaway guardrail is below.
- **Cost guardrails target the runaway, not creep** ([CRMA-497](https://mcclatchy.atlassian.net/browse/CRMA-497)). Creep stays with the audit agent's daily cost rollup. Every extracted agent service carries two guardrails:
  - **Per-run cap:** a service that runs `services/lib/gemini_loop.mjs` passes an explicit `budget_usd` of about 2× its observed max run cost — never the $5.00 default. **Enrichment: $1.00** (all-time max $0.52).
  - **Rate alert:** one Cloud Monitoring policy per service on `run.googleapis.com/request_count`, threshold about 4× its largest normal hour (measured from its ledger before cutover), sent to the email channel **"Trend Tree alerts: mmena@mcclatchy.com"**. **Enrichment: more than 16 requests in a rolling 60 minutes.** A backfill trips it by design.
  - **The policy is code:** `services/<name>/alert-policy.json`, applied idempotently by `services/deploy.sh` on deploy. No console-only policies.
  - **Not in the template:** no in-service daily ceiling (costs code and a backfill override against ~$140–260 worst-case overnight exposure); no key- or project-level cap (needs grants we lack, and the one Gemini key is shared by every service in the project); no `billing-*` labels (they attribute only ~$1/mo of Cloud Run compute to a billing account nobody here can read — add them only if finance asks).
  - Per-run LLM cost lives in application telemetry (enrichment: `LLM_COST_ESTIMATE` on `FCT_TREND_ENRICHMENT_LEDGER`), never GCP billing, which cannot split the shared key's spend.
- **Ingress is chosen by caller** ([CRMA-528](https://mcclatchy.atlassian.net/browse/CRMA-528)).
  - **A Pipedream workflow calls the service:** the service is public (`allUsers` invoker) and requires an API key in a request header. It rejects a missing or wrong key before any Snowflake or LLM call. The key is one Secret Manager secret per service (`trend-tree-<name>-ingress-key`), mounted with `--set-secrets`; the Pipedream side holds it as a workspace variable. Rotation is self-service: add a secret version, then update the variable.
  - **Cloud Scheduler or another Cloud Run service calls the service:** `--no-allow-unauthenticated` plus OIDC, with a per-service `run.invoker` binding. These callers get OIDC with no key.
  - **Exit rule:** when a service's last Pipedream caller leaves, remove the `allUsers` binding, delete the key secret and the Pipedream variable, and switch the service to OIDC. The public surface never outlives the transition.
  - **Phase 1–2 invocation is variant D:** the dispatcher keeps the sync chain (`sources` → enrichment → `write`) and calls the enrichment service with the header key. CRMA-443's raise-on-failure stays valid. The end-state invocation (what calls enrichment when the dispatcher is gone) is Cloud Tasks — see the scheduler constraint below ([CRMA-534](https://mcclatchy.atlassian.net/browse/CRMA-534)).

- **Cutover is an env-var flip inside a bounded rollback window** ([CRMA-444](https://mcclatchy.atlassian.net/browse/CRMA-444)). Every agent that moves while a Pipedream caller calls it follows these steps:
  - **Pre-cutover commit:** the caller always sends the ingress-key header, and a terminal `raise_failure` step throws only when the hop's URL is not a `*.m.pipedream.net` host. The commit is safe to deploy before cutover. Smoke-test `$.respond({ immediate: true })` in this commit.
  - **Replay, not shadow:** before the flip, fire about 10 already-processed inputs at the `candidate` tag URL and discard the output. Check the output schema, the reviewer score range, cost under the per-run cap, and duration under the service timeout.
  - **Cutover** sets the caller's URL env var (enrichment: `LLM_URL`) to the Cloud Run URL. **Rollback** unsets it. No commit in either direction.
  - **Window close:** the longer of 14 days and two weeks of the agent's normal run volume (enrichment: 14 days and 30 ledger rows), with zero service-caused crashes. At day 30 a person must close or roll back. Rollback trigger inside the window: a service-caused crash or a run over the per-run cap.
  - **Closing commit:** move the caller's default URL to Cloud Run, delete the env var, delete the agent's `WORKFLOW_REGISTRY` entry (it stays, marked idle, until then), and delete the workflow directory. A person deletes the workflow in Pipedream by hand. After the window, git history is the rollback.

- **The cron tier runs on Cloud Scheduler; per-item work arrives through Cloud Tasks** ([CRMA-534](https://mcclatchy.atlassian.net/browse/CRMA-534)). This is the phase-3 end state, after the dispatcher and the Pipedream crons are gone.
  - **Cron mechanism:** Cloud Scheduler only. No Snowflake tasks and no always-on conductor. The existing SQL-only `TASK_PROMOTE_*` Snowflake tasks are not part of the cron tier and stay.
  - **Target by shape:** a self-contained sweep (audit, daily-digest, gtrends-poller, revisit, the discovery lanes) is a Cloud Run Job (`KIND=job`) started by Scheduler. Per-item work (enrichment per trend, the cluster-agent per batch) is a service endpoint called by a Cloud Tasks queue with OIDC. A service tick endpoint exists only where a scheduled check decides whether work exists (the distillation watchdog).
  - **Invocation:** promotion adds one named task per promoted trend to the enrichment queue. One task per trend: the enrichment service runs sources and write in-process (the CRMA-493 rule — the service owns its write); `sources` and `write` do not survive as separate hops. One queue per invoked agent; the queue's max concurrent dispatches equals the service's `--max-instances`.
  - **Retry:** each queue sets 3 attempts with a 60 s minimum backoff. Cloud Tasks has no dead-letter queue; an exhausted task surfaces as a stuck trend in the audit agent (threshold owned by [CRMA-535](https://mcclatchy.atlassian.net/browse/CRMA-535)).
  - **Schedule as code:** every scheduled service has a standard `services/<name>/schedule.sh` (apply, `--dry-run`, `--fire`), independent of `deploy.sh`, with an explicit time zone, over one shared create-or-update helper. No Scheduler job exists without a `schedule.sh` that recreates it — `trend-tree-ecomm-poll` gets one, and `services/prediction/deploy/scheduler.sh` moves to the standard path.
  - **Precondition:** Cloud Tasks access (`roles/cloudtasks.enqueuer` for `crm-runtime@` plus queue creation). We can enable the API ourselves. If the request is denied, this invocation decision reopens; no poll fallback is designed.

The 2026-08-09 rejection of `allUsers` + shared secret no longer holds: CRMA-497 added the cost fence it lacked, and the key check runs before any LLM spend.
- [Audit & alerting parity (CRMA-443)](https://mcclatchy.atlassian.net/browse/CRMA-443) — **the Pipedream caller reports the crash; no new GCP credential** (2026-08-09). **Scope note: this is the *****transition-phase***** decision** — valid while a Pipedream caller exists, superseded at full exit by [CRMA-535](https://mcclatchy.atlassian.net/browse/CRMA-535). Most audit coverage survives the move untouched (the `enrichment` area and cost rollup read `FCT_TREND_ENRICHMENT_LEDGER`, written by `write-p_o7CWa2K`). The one lost signal is the **crash event**, and nothing up the chain backstops it — `dispatcher/orchestrate` catches the failed hop and returns `{error_message}`, `promotion` logs-and-continues. Fix: the dispatcher's **enrichment hop only** raises (rule: *a hop throws iff its target is no longer a Pipedream workflow*) — `respond` gains `immediate: true`, then a new terminal `raise_failure` step throws, preserving the curl 500-JSON debugging contract *and* emitting `$errors` on `p_8rCBgnl`. Realtime parity is **free**: the external monitor is workspace-wide and already covers the dispatcher. **No programmatic GCP reads in v1** — CRMA-441's grant stays the spec's sole credential ask. Coverage is three-layered with zero GCP credentials: CRMA-440's dark-deploy smoke test (broken-at-rest) / dispatcher raise (runtime) / Snowflake freshness (outcome). **Pattern:** when an agent leaves Pipedream, its Pipedream caller takes over crash reporting and the agent's audit-registry entry is deleted so its silence can't read as health. Ripples on [CRMA-444](https://mcclatchy.atlassian.net/browse/CRMA-444): smoke-test `immediate: true` (used nowhere in this repo) and remove the `p_xMC995w` registry entry **at** cutover.
- [Tool boundary: do the live ingest tools stay on Pipedream? (CRMA-493)](https://mcclatchy.atlassian.net/browse/CRMA-493) — **no: they move in-process as shared source clients** (2026-08-09). "Stay" lost on a fact predating the ticket — the four endpoint URLs appear in exactly two workflows, `enrichment` and `distillation-cluster-agent`, and **both migrate**, so staying means Pipedream survives phases 1–2 partly to host four thin workflows serving only Cloud Run. Separate tool *services* were rejected: an HTTP boundary no consumer requires, costing 4 deployables + 4 `run.invoker` admin asks for thin credential isolation inside one trust domain. Decided on the map's own priority — CRMA-438's 0.05 s-vs-72 s win only exists in-process. **Shape: share the *****client*****, not the tool** — `services/lib/sources/<source>.js` (auth, request, row→signal mapping) with a thin caller-shaped wrapper in `services/lib/tools/`; the fetch logic is **already duplicated** with the ingestion tier (both Bluesky files define the same `PDS_HOST` and URL builder), so the seam is named now rather than duplicated a third time in phase 2–3. **Persistence: pure fetch functions, the service owns the write, per tool call** through one shared retrying Snowflake client — which fixes an existing inconsistency for free (bluesky hand-rolls 3-attempt backoff for the transient-DB flake; the other three have no retry). Per-call not batched, so a later crash doesn't discard the run's signals. Agent-facing payload unchanged. **Branch closed by a fact:** folding `tag_signals` into the merge proc is out — `MERGE_EXTERNAL_SIGNALS` has ~10 callers across ingestion + discovery. **Sequencing:** module lands phase 1, cluster-agent picks it up phase 2, the four Pipedream tool workflows are deleted **when the last caller leaves**, not the first. Hands CRMA-442 two new secrets (xAI static key; Bluesky app-password→expiring JWT, keep minting per call) and the Snowflake **write** requirement; GDELT and Google Trends are keyless.

- [Concurrency & scaling posture on Cloud Run](https://mcclatchy.atlassian.net/browse/CRMA-496) — **Decided:** **concurrency 1 / min 0 / max 8 / timeout 480 s** for enrichment (2026-09-28): concurrency 1 isolates an unmeasured per-loop memory peak at no cost (~$1/mo either way); timeout nests inside the dispatcher's 500 s hop; max = 2× the largest promotion batch (4). - [Decide: invocation model — direct HTTP chain vs Snowflake-mediated decoupling](https://mcclatchy.atlassian.net/browse/CRMA-528) — **Decided:** Ingress chosen by caller: public service + header API key while a Pipedream workflow calls it, OIDC otherwise; phase 1-2 keeps the sync chain (variant D); end-state invocation moves to CRMA-534 (2026-09-28)

- [Cutover & rollback strategy](https://mcclatchy.atlassian.net/browse/CRMA-444) — **Decided:** Cutover = LLM_URL env-var flip after a URL-gated pre-cutover commit and a 10-trend replay (no shadow); window closes at 14 days + 30 runs (deadline day 30); registry entry and workflow deleted in the closing commit (2026-09-28)

- [Scheduler capability: how the cron tier survives without Pipedream](https://mcclatchy.atlassian.net/browse/CRMA-534) — **Decided:** Cron tier on Cloud Scheduler (sweeps as Cloud Run Jobs, standard schedule.sh per service); end-state invocation via Cloud Tasks, one named task per trend, 3 attempts; Cloud Tasks access requested on CRMA-1376 (2026-09-28)
