# Map: move the agent fleet off Pipedream to GCP

> Migrated from [mjmena/Trend-Tree#82](https://github.com/mjmena/Trend-Tree/issues/82) on 2026-08-07; comment history remains on GitHub. `#N` references in this body refer to the GitHub archive; blocking edges among then-open issues were recreated as JIRA links (repaired 2026-08-07 — the original migration had dropped them).

## Destination

A locked, handoff-ready **migration spec** for moving the **entire Trend Tree agent fleet** off Pipedream and onto Cloud Run in the shared `mcc-crm-automations` GCP project (`us-east4`). Delivered as **one reusable extraction template plus a phased migration sequence**, with the enrichment agent (`enrichment-p_xMC995w`) as the worked, prototype-backed example — not a spec per agent.

**The end state is a full Pipedream exit.** Hybrid — agents on Cloud Run, glue and cron still on Pipedream — is an explicit **transition phase**, not the destination.

| Phase | Scope | Gate |
|---|---|---|
| **1** | enrichment → Cloud Run, Pipedream dispatcher still calling it | specified end-to-end (CRMA-435–443) |
| **2** | the remaining agents, same template | → [CRMA-537](https://mcclatchy.atlassian.net/browse/CRMA-537) |
| **3** | scheduler + glue tier + monitoring redesign → Pipedream deleted | → [CRMA-534](https://mcclatchy.atlassian.net/browse/CRMA-534), [CRMA-535](https://mcclatchy.atlassian.net/browse/CRMA-535) |

Production stays live throughout this map; execution happens after handoff via `/to-prd` → `/to-issues`.

> **Amended 2026-08-09 (destination redrawn — Martin's call).** This map previously targeted **one agent** (enrichment) plus a reusable pattern, with the cluster-agent and the glue tier both explicitly out of scope. Both are now **in scope**, and the end state moved from "enrichment on GCP" to "no Pipedream". The seven decisions already locked (CRMA-435–443) all survive — they were written pattern-reusable — with one reframe: [CRMA-443](https://mcclatchy.atlassian.net/browse/CRMA-443) is now the **transition-phase** monitoring decision, correct until the dispatcher itself leaves, at which point CRMA-535 takes over.
> 
> **Earlier amendment (2026-08-09):** the destination once read "a **new dedicated** GCP project". [CRMA-437](https://mcclatchy.atlassian.net/browse/CRMA-437) reversed that — the host is the existing shared project.

## Notes

- **Motivation** (weight it in every comparison): Pipedream's testing and iteration loop feels restrictive — no local execution, no debugger, commit-to-deploy for every tweak, ~5.5-min HTTP sync cap. Dev-loop ergonomics outrank raw runtime fit.
- **Settled during charting / rechartering** (no tickets behind these): destination is a spec, not an executed migration; the spec is **prototype-backed**; the deliverable is **one template + a sequence**, never a spec per agent; enrichment is the worked example and moves first; hybrid is a transition, full exit is the end state. ~~Host is a new dedicated GCP project~~ — superseded by CRMA-437. ~~Scope is enrichment plus a reusable pattern~~ — **superseded 2026-08-09: the scope is the whole fleet.**
- **The fleet, counted 2026-08-09**: 18 workflows call an LLM API directly. Grouped logically — discovery + 4 Gemini verticals, distillation lead + subagent, the shared cluster-agent, revisit + subagent, promotion agent, enrichment, lifecycle + subagent, lifecycle-attribution + subagent, audit — plus the `grok-live-search` tool. Two boundary cases: `sources` is treated as glue but calls Anthropic at `sources-p_7NCy36w/generate_search_terms/entry.js:95`; `prediction-agent` is **not** an LLM agent despite the name (deterministic SQL).
- **Widening deletes work as well as adding it.** `distillation` and `distillation-revisit` both reach the shared cluster-agent through `$.flow.suspend`, a pattern that exists purely to dodge Pipedream's ~5.5-min HTTP cap. Cloud Run request timeouts reach 60 min, so at fleet scale that entire suspend/resume mechanism collapses into an ordinary synchronous call. **The same shape recurs one level down** — the four ingest tools are separate workflows only because a workflow is Pipedream's sole unit of reuse; on Cloud Run they collapse into library modules (→ CRMA-493).
- **Facts**: `gcloud` authed as `mmena@mcclatchy.com`. `gh` installed and authed as `mjmena`. Enrichment runs 3–5 min wall-clock, ~$0.40–0.50/run p95, one caller (`dispatcher-p_8rCBgnl`), sync contract `POST {trend_id}` → JSON. **Enrichment is read-*****mostly*****, not read-only, on Snowflake** — `tag_signals` (`enrichment-p_xMC995w/workflow.yaml:321`) runs an `UPDATE` on `STG_EXTERNAL_SIGNALS`, and CRMA-493 adds the tools' `MERGE_EXTERNAL_SIGNALS` call, so **the extracted service needs write**. (`CLAUDE.md` still says read-only — correct it at spec time.) Snowflake role is `MARKETING_ENGINEER` (not ACCOUNTADMIN); no Snowflake network policy exists, so Cloud Run egress is unblocked. **GCP observability (probed 2026-08-09): every read granted** (`logging.logEntries.list`, `logging.logMetrics.get`, `monitoring.timeSeries.list`, `monitoring.alertPolicies.list`, `monitoring.notificationChannels.list`, `errorreporting.groups.list`), **every create denied** (`logMetrics`, `sinks`, `alertPolicies`, `notificationChannels`, `uptimeCheckConfigs`) — GCP can never *push* an alert. **Every scheduler/event primitive is denied too**, including `serviceusage.services.enable` — the one capability gap standing between us and a full exit (→ CRMA-534).
- **Skills to consult**: `/grilling` + `/domain-modeling` for decision tickets, `/research` for research tickets, `/prototype` for the prototype ticket, `pipedream-synced-project` for how the current workflows are wired, `repo-pipelines` for the org's paved Bitbucket→Cloud Run road (reference, not a constraint — this repo is GitHub).
- **Live-probed permission matrix** for the whole GCP estate, including what a *full* Pipedream exit would require: [https://claude.ai/code/artifact/16293e71-766c-4188-8e6a-d47b89e48377](https://claude.ai/code/artifact/16293e71-766c-4188-8e6a-d47b89e48377)

## Decisions so far

- [Runtime comparison: gather the facts (CRMA-435)](https://mcclatchy.atlassian.net/browse/CRMA-435) — facts gathered ([write-up](https://github.com/mjmena/Trend-Tree/blob/worktree-wayfinder-crma-435-runtime-research/docs/gcp-runtime-comparison.md)): all four runtimes hold a 5-min sync request; Cloud Run's local loop is best-in-class (exact prod image via `docker run`, bare `node --inspect`); scale-to-zero ≈$0.86/mo vs $12–36 always-on; Functions gen2 is literally a Cloud Run service, so the Run-vs-Functions gap has collapsed to the artifact path.
- [Prototype: the local iteration loop for enrichment (CRMA-438)](https://mcclatchy.atlassian.net/browse/CRMA-438) — **verdict yes** (2026-08-08): the local loop is meaningfully better ([prototype](https://github.com/mjmena/Trend-Tree/tree/worktree-crma-438-local-loop-prototype/prototypes/local-enrichment-loop)). Fixture edit→rerun 0.05 s; full live run 72 s / $0.18 vs prod's 3–5 min / $0.40–0.50; debugger + 90 ms unit tests over extracted prompt builders. All-Gemini single-key conversion validated on unmodified prod prompts (prod reviewer still Sonnet — spec line for CRMA-445). Surfaced the tool-boundary decision (CRMA-493).
- [Runtime decision (CRMA-436)](https://mcclatchy.atlassian.net/browse/CRMA-436) — **Cloud Run (services), own Dockerfile-built image** (2026-08-08): only runtime with exact local/prod artifact parity (the CRMA-438 loop), scale-to-zero ≈$0.86/mo, revision-pointer rollback. Functions gen2 lost on artifact fidelity; GKE/VM on cost+ops. **Pattern: Cloud Run is the default for future agent extractions** — escaped only via recorded revisit triggers (outgrows sync HTTP / fleet economics flip / org mandate / hardware needs; list recorded from recommendation, amendable). Raise the default 5-min request timeout at deploy. Graduated fog → [Concurrency & scaling posture on Cloud Run (CRMA-496)](https://mcclatchy.atlassian.net/browse/CRMA-496), [Cost guardrails (CRMA-497)](https://mcclatchy.atlassian.net/browse/CRMA-497).
- [Code home: where does the service live? (CRMA-439)](https://mcclatchy.atlassian.net/browse/CRMA-439) — **trend-tree monorepo,** `services/enrichment/` (2026-08-08): new top-level `services/` namespace for standalone deployables (Pipedream provably ignores non-workflow dirs); cluster-agent lands as `services/cluster-agent/` later. `services/lib/` created now as the canonical shared-module home (seeded from `agents/lib`, repo-root Docker build context), governed by a direction rule — `agents/lib` accepts only marked backports of `services/lib` commits. Unblocks CRMA-440. *(The implied one-service-per-agent topology is re-examined at fleet scale on* *[CRMA-536](https://mcclatchy.atlassian.net/browse/CRMA-536)**.)*
- [CI/CD: how does a commit become a deploy? (CRMA-440)](https://mcclatchy.atlassian.net/browse/CRMA-440) — **manual scripted deploys, no CI in v1** (2026-08-08): one convention-driven `services/deploy.sh <name>` (per-service `deploy.env`; the script *is* the cluster-agent pattern), clean-tree-enforced git-SHA-tagged local amd64 build → Artifact Registry → `--no-traffic --tag candidate` dark deploy → smoke test at the tag URL → promote via traffic pointer; rollback = same command at the prior revision; no separate staging service. Deploys run as user creds. Revisit trigger: if CI is ever added, evaluate the org's Bitbucket paved road first, deploy identity via WIF — never keys. Ripple recorded on CRMA-437 (Artifact Registry + deployer IAM roles).
- [Provision the dedicated GCP project (CRMA-437)](https://mcclatchy.atlassian.net/browse/CRMA-437) — **no new project; host in the shared** `mcc-crm-automations` (2026-08-09). **Reverses the charter-time host decision.** Nothing was created in GCP and no org-admin request is outstanding. The 2026-08-07 "locked out" reading was wrong — it read the *direct* IAM binding (`roles/viewer`); `testIamPermissions` resolves **group-inherited** access via `crm@mcclatchy.com`. Recorded: project `mcc-crm-automations` (`289569404687`), region `us-east4` (estate is migrating there), Artifact Registry repo `mcc`, runtime SA `crm-runtime@…` (reused — we hold `actAs` but cannot create SAs), APIs `run`/`artifactregistry`/`secretmanager`/`cloudbuild` already enabled. **Accepted with the shared project:** no project-level cost fence (→ CRMA-497), shared blast radius via project-wide `run.developer`, namespace collisions (use `trend-tree-` prefixes), and **no GCP-native alerting** — `monitoring.alertPolicies.create` denied (→ CRMA-443).
- [Ingress auth: how does the dispatcher call the service? (CRMA-441)](https://mcclatchy.atlassian.net/browse/CRMA-441) — **authenticated Cloud Run + OIDC; no public endpoint** (2026-08-09). Deploy `--no-allow-unauthenticated`; caller sends a Google OIDC ID token. **One shared** `trend-tree-pipedream-caller@` SA bound `run.invoker` **per service** (each binding deliberate) — so the admin ask happens once for the whole fleet, not per extraction. **One-time admin-created key; rotation explicitly out of scope** (we lack `serviceAccountKeys.create`, so rotation would be a recurring admin ticket) — but **revocation stays self-service**: dropping the `run.invoker` binding makes the key inert, and that binding is the SA's entire capability. **Cutover blocks on the grant** — no interim public endpoint. Rejected `allUsers` + shared secret: Cloud Run URLs embed a per-project hash already public on sibling services, and edge-rejection beats in-container rejection on a project with no cost fence. Accepted: trust boundary is the *Pipedream project*, not the dispatcher workflow. **Contingent:** the mechanism holds under every invocation model, but *who* holds the credential is not settled → graduated fog to [CRMA-528](https://mcclatchy.atlassian.net/browse/CRMA-528).
- [Audit & alerting parity (CRMA-443)](https://mcclatchy.atlassian.net/browse/CRMA-443) — **the Pipedream caller reports the crash; no new GCP credential** (2026-08-09). **Scope note: this is the *****transition-phase***** decision** — valid while a Pipedream caller exists, superseded at full exit by [CRMA-535](https://mcclatchy.atlassian.net/browse/CRMA-535). Most audit coverage survives the move untouched (the `enrichment` area and cost rollup read `FCT_TREND_ENRICHMENT_LEDGER`, written by `write-p_o7CWa2K`). The one lost signal is the **crash event**, and nothing up the chain backstops it — `dispatcher/orchestrate` catches the failed hop and returns `{error_message}`, `promotion` logs-and-continues. Fix: the dispatcher's **enrichment hop only** raises (rule: *a hop throws iff its target is no longer a Pipedream workflow*) — `respond` gains `immediate: true`, then a new terminal `raise_failure` step throws, preserving the curl 500-JSON debugging contract *and* emitting `$errors` on `p_8rCBgnl`. Realtime parity is **free**: the external monitor is workspace-wide and already covers the dispatcher. **No programmatic GCP reads in v1** — CRMA-441's grant stays the spec's sole credential ask. Coverage is three-layered with zero GCP credentials: CRMA-440's dark-deploy smoke test (broken-at-rest) / dispatcher raise (runtime) / Snowflake freshness (outcome). **Pattern:** when an agent leaves Pipedream, its Pipedream caller takes over crash reporting and the agent's audit-registry entry is deleted so its silence can't read as health. Ripples on [CRMA-444](https://mcclatchy.atlassian.net/browse/CRMA-444): smoke-test `immediate: true` (used nowhere in this repo) and remove the `p_xMC995w` registry entry **at** cutover.
- [Tool boundary: do the live ingest tools stay on Pipedream? (CRMA-493)](https://mcclatchy.atlassian.net/browse/CRMA-493) — **no: they move in-process as shared source clients** (2026-08-09). "Stay" lost on a fact predating the ticket — the four endpoint URLs appear in exactly two workflows, `enrichment` and `distillation-cluster-agent`, and **both migrate**, so staying means Pipedream survives phases 1–2 partly to host four thin workflows serving only Cloud Run. Separate tool *services* were rejected: an HTTP boundary no consumer requires, costing 4 deployables + 4 `run.invoker` admin asks for thin credential isolation inside one trust domain. Decided on the map's own priority — CRMA-438's 0.05 s-vs-72 s win only exists in-process. **Shape: share the *****client*****, not the tool** — `services/lib/sources/<source>.js` (auth, request, row→signal mapping) with a thin caller-shaped wrapper in `services/lib/tools/`; the fetch logic is **already duplicated** with the ingestion tier (both Bluesky files define the same `PDS_HOST` and URL builder), so the seam is named now rather than duplicated a third time in phase 2–3. **Persistence: pure fetch functions, the service owns the write, per tool call** through one shared retrying Snowflake client — which fixes an existing inconsistency for free (bluesky hand-rolls 3-attempt backoff for the transient-DB flake; the other three have no retry). Per-call not batched, so a later crash doesn't discard the run's signals. Agent-facing payload unchanged. **Branch closed by a fact:** folding `tag_signals` into the merge proc is out — `MERGE_EXTERNAL_SIGNALS` has ~10 callers across ingestion + discovery. **Sequencing:** module lands phase 1, cluster-agent picks it up phase 2, the four Pipedream tool workflows are deleted **when the last caller leaves**, not the first. Hands CRMA-442 two new secrets (xAI static key; Bluesky app-password→expiring JWT, keep minting per call) and the Snowflake **write** requirement; GDELT and Google Trends are keyless.

## Not yet specified

- **The reverse leg: GCP → Pipedream.** Narrowed by CRMA-493 — it is no longer about tool endpoints (those move in-process), but it did **not** dissolve. `distillation-p_mkCBBqb/dispatch_to_cluster_agent/entry.js:41` allocates a `resume_url` via `$.flow.suspend()` and embeds it in the payload; the cluster agent POSTs its result **back** to that URL. So in **phase 2** — cluster-agent on Cloud Run, distillation lead still on Pipedream — a Cloud Run service calls into Pipedream. The exposure is a single unguessable capability URL rather than four public endpoints, a materially better posture, and it dissolves entirely at phase 3. Sharpens with CRMA-537's sequence (if the lead and the cluster-agent move together, it never exists).
- **What "pattern-reusable" concretely requires** — the extraction template checklist that phase 2 copies for each agent; emerges from the code-home / CI / auth / topology decisions rather than preceding them, and is assembled in CRMA-445. (CRMA-443 contributed its first two lines: flip the caller's hop to a raise, delete the agent's audit-registry entry. CRMA-493 contributed a third: tool workflows do not follow an agent as services — their fetch logic lands in `services/lib/sources/`, and the workflow is deleted when its last Pipedream caller is gone.)
- **Decommissioning Pipedream** — per-workflow teardown, the org/project itself, the `API_KEY_PIPEDREAM` workspace variable, and the GitHub sync that makes a commit to `production` a deploy. Phase-3 cleanup; sharpens once the sequence and the scheduler decision land. (CRMA-493 adds four tool workflows to the teardown list, plus repointing `scripts/test_distillation.sh` and `scripts/gdelt_category_experiment.sh`, which call the tool endpoints directly.)
- **What replaces the repo's deploy model.** A commit to `production` currently **is** the deploy, for every workflow, via Pipedream's GitHub sync. At full exit that mechanism is gone and CRMA-440's `services/deploy.sh` is the only path — which means `CLAUDE.md`'s central deploy contract, and the repo's whole shape, changes. Sharpens with the sequence.
- **Local dev credentials** — how a developer's machine gets Snowflake + LLM keys for the local loop; sharpens with the secrets decision and the prototype. (No GCP runtime's metadata-server credentials exist locally — local dev falls back to Application Default Credentials on every runtime. `snow` CLI SSO needs interactive click-through when its cached token expires; the prototype reads the LLM key from env or macOS keychain `gemini-api`.) **CRMA-493 widens this**: the local loop now also needs the xAI key and Bluesky app password to exercise tools in-process.

## Out of scope

- **Executing the migration** — the map ends at the locked spec; implementation is post-handoff work.
